Architecture

Request flows left→right through specialist agents; each handoff is a validated data contract. A central orchestrator plans and sequences; shared services sit underneath; evaluation, observability, and governance wrap the whole system.

How it stays production-grade

Evaluation

Pre + post launch

Pre: golden-campaign benchmarks, policy pass-rate, targeting precision/recall, synthetic-user E2E, regression on model/prompt swaps. Post: incremental lift vs holdout, conversion, override rate, compliance incidents.

Observability

Trace every run

Full trajectory per run — goal → plan → each agent step → tool calls → approval → activation — with a stable ID. Per-agent success / latency / cost dashboards + drift alerts.

Governance

Safe by construction

Policy enforced in the harness (not the prompt); data contracts at each boundary; immutable versioned state + audit trail; least-privilege tools per agent; HITL gate before anything sends; no monolithic agent.

Guardrails — where each one lives

Guardrails are a layer, not a component. The rule: they live in the harness (orchestration code) and the tool / MCP layer — deterministic code — never in the prompt. Rely on the prompt for safety and you're one jailbreak from a production incident.

What counts as a guardrail

Resource / loop

Stop runaway

max tool calls · max reasoning steps (loop cap) · agent-hop / recursion depth · token + cost ceiling · timeouts · concurrency caps

Resilience

Survive dependencies

circuit breakers · retries + backoff · rate limits · fallbacks / graceful degradation · idempotency keys

Input

Guard what goes in

prompt-injection detection & sanitization (incl. tool outputs re-entering context) · PII redaction · moderation · input schema validation

Output

Guard what comes out

schema / format validation · groundedness & citation checks · policy & compliance (brand / legal / reg) · DLP / PII-leak · confidence thresholds

Action / authz

Guard what it does

least-privilege tool scoping · read-vs-write separation · allow / deny lists · human approval on irreversible actions · dry-run · spend / volume caps · rollback (saga)

Data / consent

Guard the data

data contracts at handoffs · consent + suppression + frequency caps · attribute / PII access scoping · context-window hygiene · kill switch

Access & promotion — RBAC

Internal, but not everyone can create — and nothing an agent builds goes live without a human. The model rests on two identity planes and a sandbox → prod promotion boundary.

Two identity planes

Human RBAC

Which people can do what

Trigger a run · approve / validate · promote to prod · override · admin. Enforced at the orchestrator + each target system's own RBAC.

Agent RBAC

The agent's own machine identity

Each agent runs under its own scoped service identity — not the user's. Enforced at the tool / MCP layer with short-lived, per-run scoped tokens.

Agent RBAC — three rules

  • Per-agent least privilege (isolation): Audience agent → Adobe B2B CDP only; Outbound → Marketo only; etc. No monolithic all-tools agent.
  • On-behalf-of intersection: an agent's effective rights = intersection(agent's grant, the triggering user's grant). It can never do something the initiating human couldn't — no escalation through the agent.
  • Sandbox-only write, never prod: agents create in dev sandboxes of Adobe B2B CDP, Marketo, IXP, and Campaign Manager; they hold no prod-write token.

Sandbox → prod — think GitOps: the agent opens the PR, the human merges

  • Agents build the campaign / segment / experiment in the dev sandbox → low blast radius.
  • Validation agent runs synthetic-user / dry-run in the sandbox; the agent emits the prod change as a versioned config / diff.
  • HITL gate: a human reviews the sandbox artifacts + eval results.
  • On approve, a promotion service applies the change to prod under the approver's identity — atomic, reversible (saga), audit-logged. The agent never holds prod-write.
