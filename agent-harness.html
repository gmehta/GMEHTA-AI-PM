The Harness: What Holds a Team of Agents Together

One model with a few tools is an agent. Getting a group of them to work as a single system takes a harness. Here is what lives inside it.

GM
Gaurav Mehta
Jul 1, 2026 · 6 min read

Last time I wrote about the gap between an agent demo and an agent you can actually run in production. Memory, retrieval, guardrails, evaluation, observability, governance. All the parts that never show up in the demo but decide whether the thing holds up.

This piece goes one level down, into a single part of that picture that quietly does most of the work: the harness.

A quick definition. The harness is the code around the model. Not the model itself, and not the tools it calls, but the driver code in between that decides what runs, in what order, with what context, and whether the result can be trusted. With one agent you can get away with a thin harness. When an orchestrator is handing work to a dozen specialized sub-agents, the harness is most of the system. It is the difference between a pile of clever agents and a team that actually finishes the job.

I have been building this out for a multi-agent setup, where one orchestrator routes tasks to sub-agents that each carry their own skills and tools. Here is how I have come to think about it, in five layers. The diagram below is live, so press play and watch a request move through the whole thing, or click any box to see what it does.

01

Orchestration and routing

This is the control layer. It decides what happens and which model does it.

At its center is a loop. The orchestrator reasons about the request, takes an action, observes the result, and goes again. That much is standard. What changes in a multi-agent system is that the loop also has to track other loops. When the orchestrator hands a task to a sub-agent, that sub-agent runs its own reason-act-observe cycle, and the orchestrator has to know which of those are running, which are paused, and what each one is waiting on.

Two pieces sit next to the loop. A model router picks the right model for each agent, because you do not want your most expensive model doing simple triage. And a registry defines the sub-agents that exist: what each one is for, what it expects as input, and what it is allowed to touch.

02

Capabilities: tools and skills

Here is a distinction that took me a while to appreciate. There is a difference between knowing how to think about a task and being able to act on it. Skills are the first. Tools are the second.

A skill is a procedure, a standard operating procedure written out in full. The catch is that if you paste every procedure into the prompt, you drown the agent before it starts. So you split it in two. A catalog holds just the names and short descriptions, light enough to keep around all the time. The full instructions live in a library, and they only get injected into the agent's context once it picks that skill off the catalog. The agent discovers what it needs, then loads it. Nothing more.

Tools are the other half. These are the functions an agent can actually run: an API call, a database query, a bit of code. A tool registry holds them and, just as important, scopes them, so a given tool is only available to the agents that should have it. Protocols like MCP are how that wiring gets done in practice.

03

State and memory

Agents that work together have to pass things between them, and that hand-off is trickier than it sounds.

When the orchestrator sends a task down to a sub-agent, someone has to package the right context to go with it. The relevant documents, the results of a retrieval query, whatever state matters for that specific job. And when the sub-agent finishes, someone has to pull out its answer and carry it back up without dragging the entire transcript along, or you blow the token budget in a couple of hops. That packing and unpacking is a real job, and it belongs to this layer.

04

Governance and reliability

This is the layer that keeps an autonomous loop from doing something you cannot take back.

The most useful idea here is verification that happens outside the model. An agent will tell you, with total confidence, that it wrote the file. Verify is the code that actually checks the file is there. If the check fails, you do not just stop, you feed the failure back to the agent so it can try to fix its own mistake. That one habit, proving success with code instead of trusting the model's word, catches a surprising amount.

Around that sit the guardrails: hard limits on how many times a loop can run, caps on how much it can spend, and validation on what goes in and what comes out. None of it is glamorous. All of it is what lets you sleep.

05

Operations

The last layer is visibility. Every decision the orchestrator makes, every skill it injects, every tool a sub-agent fires, every metric, all of it gets logged across the whole graph. When something goes wrong in a multi-agent run, and it will, tracing is the only thing that lets you answer the question that actually matters: what did this agent see, and why did it decide that?

Putting it together

None of these layers is interesting on its own. The point is how a single request moves through all of them. Here is the pattern, start to finish.

  1. 01Task assignment. The orchestrator takes in a complex request and opens its loop.
  2. 02Discovery. It checks the skill catalog and the sub-agent registry to see what can help.
  3. 03Routing. The model router spins up the right specialized sub-agent.
  4. 04Context load. The context manager injects the state that sub-agent needs.
  5. 05Execution. The sub-agent pulls its procedure from the skill library and acts through the tool registry.
  6. 06Validation. The harness runs a verify check, inside the guardrails, on whatever came back.
  7. 07Return. The verified result is logged through observability and handed back to the orchestrator, which decides what happens next.

Seven steps, and the agents themselves are really only in charge of one of them. The rest is harness.

Why this matters

If you take one thing from this, it is that the intelligence is not the hard part anymore. The models are good and getting better every few months. The hard part is everything that surrounds them: the routing, the context you pass, the checks you run, the trail you leave behind.

A demo skips all of it and still looks great. A production system cannot, and that is exactly why the harness is where I spend most of my time. Map your own system against these five layers and be honest about which one is thinnest. That is usually the one about to give you a bad week.
