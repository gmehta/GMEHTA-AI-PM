Composed from 6 shared blocks
The unification in one line: an App is a composition of blocks that renders a surface; an Agent is a composition of (mostly) the same blocks that takes actions. Because they're built from one library, anything you make in one is reusable in the other — no rebuild, no second product.

Block Library

The primitives every app and agent is composed from. A block is built once and reused everywhere — the same Splunk data feed, failover runbook, or change-approval action powers both a dashboard and an autonomous agent. The library is the moat; apps and agents are just compositions.

Reuse is the point: see how the same blocks appear under "used in" for both an app and an agent. When a customer encodes a runbook once, every future app and agent inherits it — knowledge compounds.

My Workspace

Apps and agents live together, not in separate tools — because they share blocks. The badges show which blocks each build reuses from the library.

Bring your own coding agent

The power lane. Engineers and AI coding agents (Claude Code, Cursor, Codex) build against the same blocks via a spec, a CLI, and MCP tools. Anything composed in the visual builder is a spec an agent can pull, edit, and push back — and vice versa. Two paths, one block model.


    

    
Neither path is a second-class citizen — the seam is the product. The free tier keeps BYO-agent access rate-limited but open, because builders who arrive with their own agents are the ecosystem's most influential users.

  


  
  

    
Marketplace

    
Certified Cisco and partner apps, agents, and blocks — deploy in one click, governed the moment they land. Partners publish reusable blocks too, so the ecosystem compounds the library, not just the app count.

    

    
The unsolved frontier (and a PM owns it): a customer- or partner-published agent acting on production infrastructure is a real liability surface. Certification tiers, runtime policy via AI Defense, versioned/immutable publishing, and a clear accountability model are how you open the Marketplace without the first bad agent poisoning trust.

  


  
  

    
Governance & the read → act ladder

    
Governance is a primitive, not a tax. Every block carries scope; every action is checked at runtime. The further up the ladder a build goes, the more guardrails engage — which is exactly what makes letting agents act on production infrastructure safe. Click a rung.

    

    

    

      
⛨ AI Defense
Runtime policy enforcement + continuous scanning. You define what each block/agent can do, when it can act, and what needs human approval.

      
👁 Splunk AI Agent Monitoring
Every execution traced and observable — the audit and forensics layer for human + agent action.

      
🔐 Inline RBAC
Least-privilege translated across product boundaries. Relevance never grants action — scope does.

    

  


  
  

    
Commercial model

    
Confirmed chassis: three platform tiers (Essentials / Advantage / Premium), Cloud Control entitlement-included at the lower tiers, token packs a la carte. Studio's own line is open — here's how I'd price it.

    
The one value metric: governed production action. Free to build & preview; you pay when a build runs in production and acts, at scale, governed. It's honest (price tracks value), defensible (ties to the moat), engine-agnostic (App Builder or BYO — you monetize the harness, not the model), and it never gates the craft loop.

Watch-outs: don't price the existence of action (chills tier-4 adoption) — price scale; offer committed bundles so variable token bills don't spook enterprises; the metric is only as good as the metering instrumentation.

  


  
  

    
Design rationale

    
Why this redesign, and the PM thinking behind it.


    

      
The problem I'm solving

      
Today App Builder (prompt-to-app, Codex) and Agent Builder (describe-agent + runbooks + connectors + sandbox) are two distinct flows, plus a BYO coding-agent path. Cisco's own #1 stated design problem is making them feel like one product, not two. If they stay siloed, builders learn two mental models, blocks get rebuilt in each, and the seam leaks.

    


    

      

        
The thesis: composable building blocks

        
Make the primitives the product. Data, Skills, Actions, and Surfaces are built once and composed into either an app (renders a surface) or an agent (takes actions) — or both. Unification isn't a shared login bolted over two tools; it's a shared substance. Move between app and agent with zero rebuild.

      

      

        
Why it's strategically right

        
    
          
  • Maps to the read → act ladder: apps lean read, agents lean act, same blocks underneath.
    • 
          
  • Knowledge compounds — encode a runbook once, every future build inherits it.
    • 
          
  • Governance attaches to blocks, so it's consistent across apps and agents.
    • 
          
  • The BYO lane reads/writes the same blocks — power users never fork the model.
    • 
        

      

    


    

      
Challenges this design has to keep honest about

      

        
⚠ The seam, for real
"One block model" must hold under the hood — a composed agent and a hand-built BYO agent must emit identical artifacts, or the seam reappears.

        
⚠ Block sprawl
A shared library only compounds if it's curated — versioning, ownership, and discovery of blocks become a real product surface (and a Foundations dependency).

        
⚠ Memory & context
Agents need durable memory beyond a build. Is that a Foundations primitive every block inherits, or DIY? Today it's a frontier — the design assumes it becomes a block type.

      

    


    

      
What changed vs. my v1 (Mini-Studio)

      
v1 proved the prompt-to-app loop + BYO + commercial model. v2 adds the missing half — Agent Builder (runbooks→skills, sandbox, ambient/Canvas deploy, governance) — and reframes the whole thing around shared blocks so apps and agents are one product, matching Cisco's actual App Builder + Agent Builder design language.
