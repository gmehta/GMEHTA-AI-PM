Migrate.ai — Migration Intelligence for a 200-Campaign Cutover

How I designed a complexity-scoring dashboard to sequence a large-scale Eloqua → Marketo/AEP migration — turning 2 months of manual triage into a data-driven migration plan with a hard 7/31 deadline.

The Problem

Intuit GBSG (Global Business Solutions Group) was undertaking a large-scale migration of its entire marketing operations stack — from Oracle Eloqua + Segment CDP to Adobe Experience Platform (AEP) + Marketo — with a hard cutover deadline of July 31. That meant migrating approximately 200 campaigns and 400+ audiences in a tight window.

The core challenge: No one knew which campaigns were safe to migrate immediately, which needed extensive engineering support, and which were so intertwined they couldn't migrate alone. MOps was facing the prospect of manually inspecting hundreds of Eloqua canvases — a multi-month effort that the deadline wouldn't allow.

The existing institutional knowledge about campaign complexity lived in spreadsheets, Slack threads, and in the heads of 3–4 senior MOps partners. There was no shared, queryable understanding of campaign topology — no way to answer "What are the 20 most complex campaigns?" or "Which ones can I migrate this sprint without breaking dependencies?"

Key Insight: Topology-First Prioritization

The central product insight was that not all 745 campaigns are equivalent migration units. The most useful segmentation wasn't by business unit, geo, or campaign type — it was by how a campaign gets its audience:

🔴 Harder — Program-Routed
187 campaigns
Entry via program logic. High canvas complexity, multi-step upstream chains, possible SCC loops. Need Marketo program architect, not just Smart List migration.
🟢 Faster — Segment-Sourced
52 campaigns
Entry via Segment audience criteria only. Maps cleanly to a Marketo Smart List. Best candidates for early migration waves with minimal engineering risk.

This segmentation became the migration team's primary sequencing heuristic. The 52 segment-sourced campaigns could be scoped as Wave 1 with high confidence, buying time for the more complex program-routed work.

5

Key Design Decisions & Tradeoffs

📐
3-Dimension Complexity Scoring over Raw Counts
Rather than counting canvas steps (a noisy signal), I scored each campaign across three orthogonal dimensions: canvas complexity (branching depth, loops, wait conditions), upstream complexity (chain depth, max chain depth), and migration dependency (how many other campaigns must co-migrate). This gave actionable buckets — not just a list sorted A-Z.
🕸️
Interactive Flow Map for High-Complexity Ecosystems
For flagship journey ecosystems like ELM5334 (125 nodes, 214 edges, 56 campaigns), a table view is insufficient. The D3.js force-directed graph lets MOps see the full dependency web interactively — which nodes are in SCC loops, which are seed clusters, which are isolated. This turned a 56-campaign planning problem into a 5-minute visual scan.
⚡
Static Snapshot over Live API
The tool was built to answer "what is the current migration landscape?" not "what changed in the last 5 minutes." Embedding JSON snapshots kept the tool portable (no backend required), fast (zero API latency), and resilient to Eloqua API rate limits during the sprint. The tradeoff: data currency is manual — but for a bounded migration project, that was acceptable.
🔍
Baked-in PM Guidance in UI Copy
The Segment-Sourced view explicitly says: "Best candidates for direct Smart List migration." The Program-Routed view surfaces SCC loop counts and co-migration numbers. The tool doesn't just display data — it encodes the migration team's heuristics so any new MOps partner can onboard in minutes without a knowledge-transfer session.

Architecture Overview

V1 (the "vibe-coded" version shown in the Live Demo) was deliberately scope-constrained: a read-only analytics layer with zero backend dependencies. This made it shippable in days, not weeks.

Data pipeline: Eloqua REST API → local SQLite → Python ETL scripts → JSON snapshots bundled into vanilla HTML dashboards → AppFabric Web Plugin wrapper. The KG and force-directed graph were computed offline and embedded directly into the page.

V2 (AgenticMOps) extends this foundation: the complexity scores and KG topology from Migrate.ai became the training corpus for the Audience Agent and Campaign Assembler in AgenticMOps — sibling campaign mining uses the same graph structure that Migrate.ai visualized.
7

Reflections & What I'd Do Differently

Build the scoring model with MOps, not for them. The first version of the 12 challenge types was largely self-derived from canvas inspection. Getting MOps partners to validate and rank the challenge types earlier would have improved prioritization accuracy — and built buy-in before the migration waves started.
Co-migration count was underweighted. I initially focused on canvas complexity; the migration team's biggest friction ended up being hidden co-migration dependencies — campaigns that couldn't migrate until their dependencies did. The dependency view should have been the primary sort, not a filter.
The ELM5334 flow map validated the graph-first approach. When the migration PM saw the force-directed graph of 125 nodes and 214 edges, the reaction was: "I've never seen the full scope of this journey before." That moment — turning hidden institutional complexity into an inspectable artifact — became the core value proposition for AgenticMOps' knowledge graph.
A snapshot tool has a shelf life. The v1 approach was right for the sprint, but its limitation is data freshness. The agentic v2 architecture — where agents read live from Eloqua, Segment, and AEP — solves this at the cost of significantly higher system complexity.
