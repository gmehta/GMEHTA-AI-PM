AgenticMOps — Compressing Campaign Launch from Months to Minutes

How I architected a 7-agent platform that transforms campaign operations at Intuit — replacing weeks of human-in-series coordination with a parallel agent pipeline and a living knowledge graph of 20,000+ marketing nodes.

The Problem

At Intuit SBSEG (Small Business Solutions Group), launching a marketing campaign takes 2 weeks to 2 months. That's not a technology bottleneck — it's a coordination bottleneck. Humans work in series across six platforms: QuickBase (brief) → AEP (audiences) → Marketo (journey) → Campaign Manager (activation) → PPM (offers) → IXP (experiments). Each step waits for the prior team to finish before the next starts.

The compounding cost: With ~1,000 campaigns per year across TurboTax and QuickBooks, even a modest 2-week average launch time means hundreds of person-weeks burned annually on handoff coordination — not on strategy or creative thinking. Institutional knowledge (attribute paths, suppression rules, holdout policies) lives in 3–4 senior MOps heads with no scalable transfer mechanism.

Existing tooling addressed individual platforms, not the whole. There was no system that could take a campaign brief and drive parallel, coordinated work across all six platforms simultaneously — with human review gates, not human execution.

2

Product Vision

"SOT to launch in a single working day."

The target state: a marketing ELM fills in a QuickBase brief (the Source of Truth). From that moment, agents drive every subsequent step — audience build, journey configuration, offer assignment, experiment setup, creative generation, and E2E validation — in parallel, with human review gates before any platform promotion. MOps partners move from hands-on-keyboard to strategic reviewers.

The shift in mental model: MOps stops being execution labor and becomes a quality assurance and strategy function. The agents handle the "how"; humans own the "what" and the final GO/NO-GO.

The Agent Architecture

The full vision is 7 agents operating across 4 phases, with a shared knowledge graph as the substrate. The current POC demonstrates the core Audience + Creative + IXP agents live.

Phase 1
SOT Intake Agent
Parses QuickBase ELM brief (65+ fields) into structured Campaign node in KG. Blocks all downstream agents until Gaurav approves the extracted spec.
Phase 2 — Parallel
Audience Agent
KG-first sibling mining → Segment CDP trait resolution → AEP audience build → CDC DQ validation. Retries up to 3× before routing to HITL.
Phase 2 — Parallel
IXP Agent
SOT experiment parsing → creates A/B experiment in IXP E2E with arms, splits, hashing constant, and assignment ID type.
Phase 2 — Parallel
Creative Agent
Figma file → per-frame HTML generation → Marketo Design Studio deployment. First agent promoted to production (IKS AIR).
Phase 2 — Parallel
Offer Agent
PPM offer assignment and Capital offer upstream resolution. Shares KG Audience Spec context with Audience Agent.
Phase 3
Campaign Assembler
Waits for all Phase 2 agents. Assembles validated components into a unified campaign spec. Routes to Gaurav for final GO/NO-GO gate.
Phase 4
E2E QA Agent
Synthetic test-user harness. Fetches email HTML, sends test messages, validates rendering and deliverability before production launch.
HITL design principle: Every agent completes its work autonomously then routes to the domain expert for approval. Gaurav is the final approver on Phase 1 (intake) and Phase 3 (assembly). No agent promotes to production without a human gate.

The Knowledge Graph as Substrate

The most important architectural decision in AgenticMOps was making the campaign knowledge graph the shared substrate for all agents — not an optional enrichment layer. Every agent reads from the KG before deciding, and writes back to it after acting. This means agent intelligence compounds over time.

The Audience Agent's sibling-campaign mining uses Neo4j Cypher to find structurally similar historical campaigns (cosine similarity on audience fingerprints) — then mines their validated attribute resolutions as a starting point. This eliminates cold-start for every new campaign build.

Drift detection design: The KG tracks four dimensions of planned-vs-actual state using REALIZED_BY relationships: Data Attributes, Audiences, Campaign Design, and IXP Experiments. This lets agents detect when a live platform diverges from the SOT spec — and route the delta to the right owner automatically.

Key Design Decisions

🎯
Agents Own Outcomes, Not Platforms
I could have named these "AEP Agent," "Marketo Agent," etc. Instead: Audience Agent, Journey Agent, Creative Agent. The distinction matters — a platform agent is a wrapper; an outcome agent has a goal and makes decisions to reach it across however many platforms that goal requires. This shapes the agent's decision surface, its failure modes, and how humans review its output.
🗓️
Build Wave Sequencing by Leverage, Not Completeness
Wave 1 (KG + SOT Intake + Audience Agent) unlocks 70% of the campaign lifecycle's value — audience is the longest pole. Wave 3 (Creative) is last because "email coding is the smallest part of the timeline today." Sequencing by leverage meant the POC delivered measurable speed improvement months before the full platform was complete.
🔬
Journey + Campaign Manager as One Agent
Journey Agent owns both Marketo and Campaign Manager — deliberately unified. Splitting them recreates the exact coordination problem the agents are meant to eliminate. One customer experience means one agent that can reason end-to-end, not two agents that need to hand off to each other.
📖
Heuristics as First-Class KG Nodes
Platform conventions (naming schemas, suppression patterns, holdout rules) are encoded as Convention nodes in the KG rather than hardcoded in agent prompts. When a convention changes, one KG node update propagates to all agents that query it — no prompt engineering required.
🚫
"Extract Only — Never Assume" Guardrail
The SOT Intake Agent has a hard constraint: never infer or fabricate a field value. A missing audience attribute is left blank, not guessed. The rationale: false positives in campaign configuration (wrong suppression, wrong IXP arm) are far more costly than gaps that a human reviewer catches at the approval gate.

The KG is the defensible asset. Agent prompts can be rewritten; the 20,000-node knowledge graph of validated attribute mappings, historical campaigns, and platform conventions cannot be replicated quickly. Building the KG first was the right call — every subsequent agent gets smarter for free.
Stage 2 → 3 readiness warning. The current "Read and Compose from SOT" skill set doesn't survive the shift to goal-driven design. The durable investment is the KG + Build/Verify/Act agent pattern. I've documented this as an architectural boundary so future agents don't regress to prompt-only designs.
