📋 Product Brief

Personal OS — An AI-Native Command Center for a Senior PM's Async Life

How I built my own personal operating system: a local-first, file-backed Slack triage dashboard with AI routing, human-in-the-loop reply approval, Notion task sync, and a knowledge graph — so I can stay ahead of a high-volume async workstream without constant context-switching.

The Problem

As a Staff PM leading GTM Tech at Intuit, I operate across multiple high-stakes concurrent workstreams: a 200-campaign Eloqua→Marketo migration with a hard 7/31 deadline, an agentic AI platform being presented to CTO leadership, and a parallel job search. The throughput problem isn't meetings — it's async communication that doesn't stop.

The core constraint: My Slack surface in a typical week generates 50–100+ @mentions and DMs across group threads, direct messages, and migration coordination channels. Manual triage — reading, prioritizing, drafting, sending — consumed multiple hours daily. The cognitive cost of context-switching between a high-priority "are we still joining zoom?" and a low-priority informational update is asymmetric and cumulative.

Standard approaches (Slack saved items, notification batching, labels) don't solve the underlying problem: the reply still requires me to context-switch, compose, and decide. What I needed was a system that could make those decisions for me — and present completed drafts for a single-click approval.

Design Goals

⚡
Zero Outbox Surprises
No AI message ever sends without my explicit approval. Every draft surfaces in an inbox — I approve, edit, or reject. The system defaults to "human decides."
🧠
Context-Aware Routing
Routing decisions use sender identity from the Neo4j KG — not just keywords. A message from my manager (Deepak) routes differently than the same words from an unknown colleague.
📁
Local-First, No SaaS Lock-In
State lives in JSON files on disk — portable, auditable, git-trackable. No subscription, no cloud vendor dependency for core functionality.
🔁
Learning from Approvals
Every approve/reject decision is logged to routing-feedback.json for future routing improvement. The system gets better the more I use it.
🛠️
Extensible via MCP
Airtable, Eloqua, Outlook, Databricks, Obsidian, Segment CDP, Neo4j — all accessible from the same agent surface via MCP servers, without building custom integrations.
📓
Mandatory Memory Logging
Every meaningful agent action appends to memory.md. The audit trail is a feature — it enables the JobMagic skill to pull verified facts for resume generation without fabrication.

System Architecture

The system has three layers: a dashboard (browser SPA for triage), an orchestrator (always-on Node.js daemon for Slack events), and a knowledge graph (Neo4j for sender context and personal memory).

Refresh pipeline (5 phases): Scheduled messages check → @mentions fetch → DMs fetch → Tracked thread poll → GenOS classification → Agent inbox → Human approval → Pending replies queue → Slack send. Every step is logged; every send gate requires my action.

The Routing Intelligence

The most PM-critical design decision was the routing matrix — how the system decides which messages need me immediately, which can be drafted by an agent, and which can be fully automated. The matrix combines sender criticality (from KG) with message complexity (from GenOS classification):

SenderComplexityRouting DecisionPattern Name
VIP (manager, skip-level, exec) High Human Only Direct Intervention
VIP Low Hybrid — draft & veto Draft & Veto
Peer + Active Project High Hybrid — scope & route Scope & Scatter
Peer + Active Project Low Agent auto-execute The Nudge
General colleague High Hybrid — intake & escalate Intake Coordinator → Escalation
General colleague Low Agent auto-execute The Vending Machine
Key guardrail: VIP + High complexity messages never reach the agent. The system surfaces them immediately in the High priority tab with the sender's KG relationship context — so when I open the dashboard, I see exactly why this message needs direct attention, not an AI draft.

Key Design Decisions & Tradeoffs

📁
File-Backed JSON over a Database
mentions.json, agent-drafts.json, top5.json, routing-feedback.json — all on disk. The tradeoff: no concurrent write safety, but the payoff is total portability, debuggability, and git-trackability. For a single-user personal system, this is the right call. If I wanted multi-user, I'd add SQLite; if I needed real-time collaboration, I'd add a proper DB.
🔀
Two Parallel Dispatch Paths (Idempotent)
The dashboard (Phase 4 flow) and the orchestrator (30s polling loop) can both trigger a reply send. To prevent double-sends, the endpoint is idempotent — a complete status on a pending reply prevents re-execution. This redundancy means if my laptop's dashboard is closed, the orchestrator still processes approvals.
🎭
Agent as a First-Class Peer, Not a Plugin
The Cursor agent accesses the same REST API as the dashboard for updates and agent draft pushes. There's no "agent mode" — the agent can do everything a human can via the API, subject to the same approval gates. This means agentic workflows and human workflows compose naturally without special casing.
🚫
Anti-Fabrication Guardrails in JobMagic
JobMagic (the resume generation skill) has a 13-point immutability ruleset: employer names, job titles, tenure dates, education, and contact info are locked and sourced from memory.md — never inferred. The KG enriches with verified accomplishments; the LLM only rephases, never invents. This was prompted by a near-miss where a first draft fabricated a plausible-but-false metric.
📊
Playbook Design: Only for Low-Complexity Patterns
Playbooks (SOPs as markdown templates) are deliberately scoped to Agent (Stateless) and Agent (Stateful) decision paths — never for VIP or High-complexity messages. The principle: playbooks codify known, repeatable patterns (e.g. Eloqua developer access requests). Novel or high-stakes situations always route to human judgment.

Integrations via MCP

Rather than building bespoke integrations into the dashboard, I used the Model Context Protocol (MCP) to expose 15+ tools to the agent layer in Cursor. This means the agent can pull Eloqua campaign data, create Airtable records, search the Obsidian vault, or query Databricks tables — all from the same conversational interface, without maintaining custom API clients.

Reflections & What I Learned Building It

Building your own tool is the best PM exercise. I am the user, designer, developer, and customer support. Every friction point is immediate and unambiguous. The dashboard has been rewritten 4 times in its column layout alone — because I actually use it daily and feel every pixel that's wrong.
The routing matrix is where the PM thinking lives. The decision about what routes to "Human Only" vs. "Agent auto-execute" encodes my values and risk tolerance. Getting that matrix wrong in either direction has real cost: over-routing to human means I'm back to manual triage; under-routing means a GenOS draft goes to my manager without review. The matrix is the product.
Memory logging is underrated. The mandatory memory.md requirement — which felt like overhead when I designed it — has become the most valuable part of the system. It created a verified, timestamped record of every significant decision, product build, and outcome. That record became the source of truth for JobMagic and for this portfolio.
The Eloqua playbook false-positive taught me about edge cases in NLP routing. The original regex-based playbook matching fired on messages that contained the word "Eloqua" regardless of intent — causing an automation draft on a message that needed human escalation. The fix (2-stage: keyword preFilter → GenOS intent classifier) is a pattern I've applied in AgenticMOps as well.
Personal OS and AgenticMOps share the same architectural DNA. The agent-as-peer design, the HITL approval gates, the KG-for-context pattern, and the playbook-as-SOP model — all originated in the Personal OS and were refined and scaled in AgenticMOps. Building the personal version first meant I shipped the enterprise version faster.
